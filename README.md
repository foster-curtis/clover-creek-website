# Clover Creek Guest House

Direct-booking website for the Clover Creek Guest House, a farm-stay vacation rental in
Rush Valley, Utah. Built with Next.js + TypeScript, Supabase, Stripe, and Tailwind, hosted
on Vercel.

- **[SETUP.md](SETUP.md)** — how to connect the accounts (Supabase, Stripe, domain, email)
  and launch. Start here.
- **[docs/LOCAL_DEV.md](docs/LOCAL_DEV.md)** — running the whole stack locally: Supabase in
  Docker, the local inbox, seed data, migrations, and Stripe webhook forwarding.
- **[DEVELOPMENT_PLAN.md](DEVELOPMENT_PLAN.md)** — the original feature plan and
  architecture decisions.
- **[GIT_WORKFLOW.md](GIT_WORKFLOW.md)** — branches, CI/CD, and the `working` → `stg` →
  `master` promotion flow.

## Features

- Availability calendar with live pricing quotes ($75 weeknights / $105 weekends &
  holidays for 2 guests, extra-guest and dog fees, cleaning & taxes included)
- Stripe Checkout payments with 30-minute date holds and database-enforced
  double-booking protection
- Guest accounts (passwordless email sign-in), booking history, and realtime chat with
  the owner
- Reviews with automatic "verified stay" badges and owner moderation
- Admin dashboard: bookings, refunds, blocked dates, manual bookings, editable site
  copy, pricing & holidays, review moderation, blog authoring, inquiries
- iCal feeds for the owner's Google Calendar and Airbnb/VRBO availability sync
- Booking confirmation / notification emails (Resend), SEO (structured data, sitemap),
  HERE map with OpenStreetMap fallback, Vercel Web Analytics

## Development

```bash
npm install
npm run dev    # http://localhost:3000
npm test       # pricing engine tests
npm run build  # production build
```

The site runs with zero configuration (booking disabled) and each integration switches
on as its environment variables are added — see [.env.example](.env.example).

To work against a real database — bookings, sign-in, the admin dashboard — run Supabase
locally rather than pointing at production: [docs/LOCAL_DEV.md](docs/LOCAL_DEV.md).

## Adding or changing photos

Photos are part of the codebase, not something uploaded through the site. That keeps
each file's dimensions and weight fixed at commit time — the main lever on how fast a
page loads — and puts alt text and captions in the diff where they can be reviewed.

The full-resolution originals live in the owner's Google Drive. This repository keeps
only the ~2400px derivatives the site actually serves.

1. **Keep the original in Google Drive.** That is the archive.
2. **Copy it into `images-src/`**, named the way you want it to appear in the URL:
   lowercase, hyphenated, ASCII, ending in `.jpg` — e.g. `front-porch-morning.jpg`.
   The folder is gitignored; the originals are never committed.
3. **Run the optimizer.**

   ```bash
   node scripts/optimize-images.mjs
   ```

   It writes `public/gallery/<name>.jpg` (max 2400px wide, quality 78, rotation baked
   in, all EXIF stripped) and prints a ready-to-paste manifest entry with the width,
   height and blur placeholder already filled in.

4. **Add the entry to [`src/content/gallery.ts`](src/content/gallery.ts)**, writing
   `alt` and `caption` yourself:
   - `alt` describes the photo for someone who cannot see it ("King-size bed with a red
     plaid patchwork quilt"). It is required — the build fails without it.
   - `caption` is the short label everyone sees under the photo in the lightbox. Don't
     make it a copy of the alt text.
   - `order` sets the position, lowest first.
   - `role: "hero"` and `role: "intro"` mark the two photos the home page features.
     Exactly one photo has each.
5. **Commit** the new file in `public/gallery/` together with the manifest change.

`npm test` checks the whole set: every entry has a file, the declared dimensions match
the real ones, alt text is present, ids are unique, no stray files are left in
`public/gallery/`, nothing carries EXIF metadata, and no served filename uses uppercase
(which works on Windows and macOS but 404s on Vercel's Linux build).

`public/og-default.jpg` is the 1200x630 social share card. It has the site name drawn
on it, so it is composed by hand rather than generated by the script — the script and
the tests only check that it keeps those exact dimensions and carries no metadata.

`docs/gallery-export.json` is the verbatim export of the photo metadata as it stood in
Supabase before the migration, and the tests check the current manifest against it so
the copy cannot silently drift.
